# Block-KOMP: block-synchronous eviction, FLA-style kernels

2026-11-01. A new operator family beside the per-token KOMP. Within a chunk of C tokens every
new key writes into its own fresh slot; the dictionary temporarily holds the M carried atoms
plus the chunk's keys. At the chunk end the newest M atoms are kept (FIFO, the block analogue of
the cyclic routing used in all KOMP experiments) and every evicted atom is jointly projected onto
them with the ridge-regularized kernel Gram (kept coefficients are not shrunk). Decay is
GDN-style: the input is the log decay g = log alpha per token and head.

This is a semantic change from per-token KOMP: eviction happens once per chunk, and inside a chunk
the memory has M + C atoms. The per-token operator is unchanged.

## Why this is the route to GDN-like cost

Per-token eviction needs one Gram solve per token. That is a serial chain, a sliding-window
kernel least-squares problem. Chunk-synchronous eviction leaves:

* Inside a chunk, a kernel delta rule. The write vector is one-hot on the token's own fresh slot,
  so the in-chunk system is C x C (`T = (I + diag(beta)(D o Hn))^-1`). It has the same UT-transform
  structure as GDN, with kernel values `Hn = k(k_s, k_t)` in place of `k k^T`.
* At the chunk end, one M x M Gram inverse per chunk and head.
* FIFO makes each chunk's dictionary a contiguous slice of the key pool. All chunk maps
  (`OS, OV, FS, FV`) therefore depend on keys only and are computed for all chunks in parallel.
  The value state then runs through the same two-level affine scan as the per-token path.

## Precision (aligned to FLA BF16 practice)

* Attention-side kernel matrices (`Hk, Hn, Rk, Rn`), the UT solve, and output maps use TF32
  products. With BF16 inputs they are stored in BF16, with FP32 inputs in FP32.
* Everything on the projection side uses tf32x3 products and FP32 storage: the Gram, its sweep
  inverse, `P k(Knew, E)`, the `J` maps, their cosine gradients, and the state maps `FS/FV`.
  A TF32 projection is 13% faster at 8k (10.72 vs 12.31 ms forward+backward). However, it failed
  the near-duplicate stress test: RMS error of dk was 1.29e-2, 8.6x the v0 error. So it is not the default.
* Output is returned in `v.dtype`.

## Next steps

* Per-slot (GSA-style) decay for Block-KOMP: decay per FIFO ring slot. In block form the decays
  become C x M and C x C log-space matrices; this needs no division.
* Key gradients as one GEMM over the union dictionary U (M+C contiguous pool rows), with fewer
  atomics. Share the Gram cosine with `Hn` when C = M.
* Fusion of stages and launch-count reduction. The per-token operator could also use the one-hot
  structure of its rank-two update.


## Round 2 (2026-11-01): per-slot decay, eviction flags, projectron, 8k speed

### Per-slot data-dependent decay (Triton, `block_fast.py`)

`g` may be `[B,T,H,M]`: log decay per physical ring slot. The atom at sequence position p (initial
atoms at -M..-1) lives in slot p mod M, which matches the cyclic routing of the per-token arms. In
block form the scalar gamma becomes a C x M matrix `Gam[t,u]=exp(Gc[t,slot_u])`. The in-chunk
decays are `D[t,s]=exp(Gc[t,slot_s]-Gc[s,slot_s])`, gathered by slot, with no division. The
log-decay gradient is scattered back to slots. Scalar decay keeps its own vector fast path.
The FP64 prototype (`komp-accel-scratch/proto/block_slot_proto.py`) matches the token reference to
1e-16. GPU acceptance:

### Eviction and projectron flags (`block_flex.py`, PyTorch chunk loop)

`block_komp_flex(..., evict='fifo'|'residual'|'coef_norm'|'learned', projectron=False, scores=None,
initial_scores=None)`:

* At each chunk end, the M highest-ranked of the M+C candidates are kept; ties go to the newer atom.
  * `residual` ranks by the projection residual 1/[(G+ridge)^-1]_aa (Schur complement).
  * `coef_norm` ranks by the coefficient norm.
  * `learned` ranks by a given score. Each atom inherits the score of its writing token; initial
    atoms take `initial_scores`.
* Evicted atoms are jointly projected onto the kept ones. Kept new atoms take their positional slot
  if it was freed, and otherwise fill the remaining freed slots in order. With `fifo` this reproduces
  the Triton FIFO exactly.
* `projectron` multiplies beta by the novelty of k_t: its ridge-regularized projection residual on
  the current dictionary, including earlier keys of the chunk. This equals the Cholesky pivots of the
  union Gram. No gradient flows through novelty or through the selection.

`block_reference.block_komp_token_reference` is a per-token reference with the same flags. All 48
combinations agree with it in FP64 to 3e-15, covering 3 shapes x scalar/per-slot decay x 4
evictions x projectron, plus tied-score cases. On GPU, both the Triton path (FIFO) and the flex
path stay within 3.3e-3 RMS of FP64. The flex path runs its Gram and solves in FP32 even inside BF16
autocast; without this, the first trial failed in Cholesky.

The value-dependent `coef_norm` makes the chunk scan state-dependent, so these flags are not yet in
Triton. The trials below use the flex path for every flag arm, and training takes about 4x longer.

## Round 3 (2026-11-01): learned eviction in Triton, cross-kernel fusion, BF16

### Learned-score eviction in Triton

`block_komp_fast(..., evict='learned', scores=[B,T,H], initial_scores=[B,H,M])` now covers the
best arm of round 2. The ranking depends only on the scores, not on the values. A serial
`dict_scan_kernel` (one program per batch-head, one step per chunk) therefore writes two tables:
the physical slot to pool row map `OLD[c, slot]` and the kept candidates `CAND[c, slot]`. All chunk
maps then stay parallel, as in FIFO. They read the dictionary through `OLD`, and selection matrices
and eviction masks come from `CAND`. Key gradients go into pool rows with FP32 atomics, so the
learned path is not bitwise deterministic. The FIFO path is deterministic. When the scores equal
insertion times, the learned path reproduces FIFO (`learned_as_fifo` checks, 1e-4).

### Cross-kernel fusion and BF16

Switches are at the top of `block_fast.py`. The defaults are the fastest combination measured.

* `FUSE_SCAN`: the scan kernels compute the chunk offsets (`FV V`, `OS^T dO`) themselves, and the
  forward expand pass also writes the outputs. The separate offset and output kernels and their
  buffers are gone.
* `FUSE_CHUNK_BWD`: out_bwd + ut_bwd + decay_bwd become one kernel.
* `FUSE_POOL_NORM`: the pool-row gradient sum and the q/k normalization backward become one
  row-block kernel. There is no DPool round trip, and the backward no longer launches one program
  per row. `ROW_NORMALIZE` does the same for the forward normalization.
* `BF16`: with BF16 inputs, attention-side products (`_adot`) run on BF16 tensor cores. The
  projection side (Gram, inverse, P, J and their gradients) stays tf32x3 with FP32 storage.
* Kept off because they were slower: `FUSE_CHUNK_FWD`, i.e. att+ut+compose in one kernel (255
  registers at 8 warps, 1 CTA/SM: 2.9 vs 1.33 ms staged), and `FUSE_PROJ_BWD`.

### Other changes this round

* Per-slot decay with C a multiple of M: g is loaded with rotated columns. FIFO old atom u lives in
  ring slot (o+u) mod M, and new atom s in slot (o+s) mod M, i.e. column s mod M. This replaces the
  register gathers, and in `chunk_bwd` also the 'ieee' one-hot product. The learned path rotates only
  its new-atom part back, with one gather. 8k per-slot `chunk_bwd`: 3.35 -> 1.80 ms.
* Key gradients, FIFO with C >= M: the kept atoms are the last M new keys. Every product with Knew
  is therefore a product with Kn, and the kept-atom gradient lands on new-key rows. The
  projection-side factors are shifted into the attention-side ones at load time
  (`_keygrad_merged`). This reduces about 22 to 13 MMA passes per program and removes the
  register-gather placement. `KEY_BLOCK` 32 -> 64.
* `dict_scan` loads the next chunk's scores one iteration ahead and runs with 8 warps; per-slot
  `ut` uses 4 warps. These were picked by one-at-a-time sweeps (`evidence/accel-20261101c/tuning-8k.txt`).
* Rejected: rank-1 Gram sweep (`RANK1_SWEEP`, off). It writes each pivot step as a single
  `a - x x^T/p` with `x = a[:, j] - e_j` and removes the 2 I offset at the end. This is the same
  mathematics and about 0.2 ms faster at 8k. However, it failed the near-duplicate bound: dk RMS
  8.4e-3 against a limit of 7.2e-3 (1.25 x v0). Flag isolation showed that only this change moves
  the error (`near-duplicate-flag-isolation.txt`, `block-rank1-sweep-failed-validation.json`).
* `KEY_BLOCK` 64 was also faster at the main and training shapes (`key-block-main-train.txt`):

## Round 4 (2026-11-01): C == M specialization, serial scan, BF16 tape, merged key gradients

Every change is a switch at the top of `block_fast.py`. The defaults are measured on H100 and
validated against FP64.

* `SHARE_GRAM` (FIFO, C == M; this is the 8k test shape). The chunk-end selection keeps all C new
  atoms and evicts the whole old dictionary, so several projection-side quantities are fixed:
  * `Nc = 0`, `PEN = 0`, and `Jn` is a pure selection. In a full chunk, `Jn = I`.
  * `proj` skips the `Knew Kn^T` product. In full chunks `Knew = Kn`, so `proj` also writes `Hk` and
    `Hn` from its tf32x3 cosines, and `att` keeps only the query products.
  * `compose` builds `FS = Jo diag(gend) + diag(dend) WS` and `FV = diag(dend) WV` without products in
    full chunks.
  * `proj_bwd_a` replaces its four tf32x3 products with row-shifted loads (`Jn^T X` is X shifted by
    M-n rows) and drops `dJn`, which is never read. `proj_bwd_b` drops the `Zn` products, and
    keygrad skips the zero `CNC`.
  * The last partial chunk keeps the general formulas.
* `TAPE_BF16`: with BF16 inputs the chunk-entry states and their adjoints are stored in BF16. Only
  `mapgrad` reads them, and it multiplies them in BF16 anyway, so the results are bitwise unchanged
  (`max-rms-vs-off 0`).
* `MERGE_KEYGRAD` improved. `F_k` is `F_old` transposed, and the two `CNC` terms are `Y + Y^T`, so
  the factors are loaded once and transposed in registers. 8k keygrad: 1.84 -> 1.42 ms.
* Fixed while adding these: Triton also compiles statements after a constexpr-if `return`. `_mdot`
  and `_adot` now use if/else, because the BF16 tape exposed a dtype error in the dead branch.
  Runtime branches whose body only type-checks under a constexpr condition must be nested inside
  that condition (`compose_kernel`).
* `SCAN_SERIAL` (one-pass serial scan). When batch-heads x value tiles >= 64, the value state runs as
  a single serial pass: `bscan_expand_kernel` with G = NC, the initial state as entry, and the final
  state written at the end. This is FLA's `chunk_fwd_h` layout, and it drops the group-compose and
  group-scan kernels. Per-chunk loads are pipelined, with the stage count capped by shared memory:
  three stages for BF16, two for FP32 at M=64. Uncapped, FP32 at M=64 needed 320 KB
  (`serial-validation-smem-oor.json`). Small batch-heads keep the two-level scan: at the main config
  the serial pass was slower (0.235 vs 0.214 ms, `ab-serial-scan.txt`).

## Round 5 (2026-11-01): hotspot study

Each idea was first measured on its own, with an op-level bitwise comparison where the change should
be exact, and then kept or rejected. Register and spill counts come from the compiled Triton kernels
(`probes-regs-warps.txt`). All probe logs are in `evidence/accel-20261101e/`.

### Kept

| change | effect at 8k | numerics |
|---|---|---|
| `QN_BF16`: normalized queries stored in BF16 (only BF16 products read them) | -0.14 ms | bitwise identical |
| `SKIP_ZERO`: no writes of the all-zero `Nc`/`PEN` under SHARE | -0.05 ms | bitwise identical |
| `DOV_BF16`: `dOV` stored in BF16 (read only by BF16 products in `chunk_bwd`) | -0.06 to -0.10 ms | bitwise identical |
| `SLOT_GC_CACHE`: `ut` stores the rotated cumulative log decay; the other four kernels load it, and read its diagonal, last row and `gend` directly instead of masked reductions | per-slot about -0.4 ms | one scan result shared by all kernels (they had ulp-level differences before) |
| `chunk_bwd` with 8 warps for per-slot decay (`WARPS['chunk_bwd_slot']`) | per-slot -0.45 ms; spills 306 -> 26 | bitwise identical |
| `OVERLAP_DICT`: the dictionary-free `Hn, Rn` and the UT solve run on a side stream next to `dict_scan` and `proj` (learned) | learned -0.22 ms | forward bitwise identical |

### Measured and rejected

* Two-select Gram sweep (`SWEEP_FUSED`). The values are bitwise identical, but it was slower: 0.89 vs
  0.82 ms standalone for 8192 inverses at 2 warps, and +0.1 ms in the operator.
* Destination-major key gradients (`KEYGRAD_DEST`). Bitwise identical. `pool_norm` dropped by
  0.09 ms, but `keygrad` grew by 0.12 ms, so the net was +0.03 ms. The DU round trip is not what
  limits keygrad.
* Newton-Schulz refinement of the rank-1 sweep (CPU float32 check,
  `komp-accel-scratch/proto/rank1_refine_check.py`). It made the error 3x worse at Gram condition
  numbers near 6e5: the FP32 residual is not accurate enough there. On CPU the rank-1 sweep and the
  standard sweep have the same accuracy, so the GPU near-duplicate failure of round 4 is a rounding
  pattern, not an algorithmic loss.
* Shorter live ranges in `chunk_bwd`: scalar `Gam` broadcast instead of materialized, and `Dp`, `Dl`
  re-formed at use in a CSE-distinct form. Bitwise identical, but spills changed only from 140 to 124
  and the time did not change. The edits are kept because they cost nothing.
* 8 warps elsewhere: scalar `chunk_bwd` +0.2 ms (1 CTA/SM); learned `proj` / `proj_bwd` +1.3 to
  +2.7 ms.
* The per-slot scan is not the cost: a [64, 64] axis-0 `tl.cumsum` runs at copy speed (0.094 vs
  0.095 ms for 8192 tiles).
* Blocked Cholesky + blocked triangular inverse (`CHOL_INV`, `chol_kernel`). The kernel computes
  16x16 Cholesky together with its inverse in one 16-step loop, does blocked forward substitution for
  L^-1, and forms Pinv = L^-T L^-1. A CPU float32 check (`proto/block_chol_check.py`) confirmed why
  round 2's block LDL failed: its explicit block inverse makes the Schur complement cancel large
  numbers (O(1) error). Cholesky keeps |L_ij| <= 1, and its P = G^-1 K is as accurate as the sweep.
  On GPU, however, it lost on both counts:
  * Speed: 8k forward+backward 7.45 vs 7.28 ms. `proj` dropped to 0.39 ms, but `chol_kernel` took
    1.20 ms at 4 warps (2.69 ms at 1 warp).
  * Accuracy: the explicit inverse is about 2.5x less accurate than the sweep's, and the backward
    multiplies by it. Near-duplicate M64/C64 dk was 1.5e-2, 2.06x the limit
    (`chol-and-c32-regression.txt`).
  In Triton the 16-blocked factorization still has 64 serial steps, each with one more reduction
  than a sweep step. Kept off.

### Regression found and fixed in this round

The first round-5 benchmark showed 8k C=32 (C < M) at 22.2 ms forward+backward, against 14.2 ms in
round 4. `att_kernel` had gone from 0.92 to 8.88 ms. Splitting it into parts for `OVERLAP_DICT` had
put runtime `if not own` branches around the accumulators in every key-block iteration, including
the non-SHARE path where `own` is always false. Those branches are now confined to SHARE.
A static pass over the other kernels found no other hot-loop runtime branch on a configuration
constant. After the fix, C=32 forward is 4.84 ms with `att` at 0.55 ms (`c32-att-fix.txt`).

Remaining limits:
* `proj` (1.43 ms) is dominated by the 64x64 sweep, which is instruction- and step-bound in
  Triton's register-tile form.
* `keygrad` (1.24 ms) runs at 255 registers with about 100 spills.
* Scalar `chunk_bwd` (1.04 ms) runs at 255 registers with about 124 spills: 8 warps removes the
  spills but costs occupancy.
* The serial value scan (0.74 ms) is close to bandwidth.
